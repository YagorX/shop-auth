# load

Нагрузочные прогоны auth **в соло-режиме**: k6 стучится в gRPC напрямую, без gateway, proxy и mTLS.

```text
load/
├── lib/auth.js    # клиент, connect, register, login, калибровка
├── validate.js    # ValidateToken — горячий путь
├── login.js       # Login — bcrypt, тест на CPU
├── refresh.js     # Refresh — транзакция ротации
├── register.js    # Register — bcrypt + INSERT
└── mixed.js       # login и validate одновременно
```

Цель — найти **колено** каждого метода: момент, когда задержка начинает расти непропорционально нагрузке. Отказы приходят позже, и ориентироваться на них поздно.

## Топология

```
k6 (docker, --network host) ──gRPC :44044──> ./bin/sso (local.yaml, TLS off)
                                                   │
                                                   ├─> Postgres :5454 (docker compose)
                                                   └─ :8082 /metrics ──> Prometheus ──> Grafana
```

TLS выключен сознательно: рукопожатие не попадает в замеры. Отличие от прода нужно держать в голове и при необходимости повторить ключевые прогоны с `tls.enabled: true` — разница и будет ценой mTLS.

## Подготовка

```bash
# 1. База и схема
task db-up && task migrate

# 2. Сервис бинарём, с фиксированным числом ядер
go build -o ./bin/sso ./cmd/sso
GOMAXPROCS=8 ./bin/sso --config ./config/local.yaml

# 3. Наблюдаемость (из shop-platform/deploy)
docker compose up -d prometheus grafana
```

`GOMAXPROCS=8` при 16 ядрах — чтобы k6 и сервис не делили одни и те же ядра. Контейнеру k6 ниже отдаётся `--cpus 4`. Без этого непонятно, чей потолок мы нашли.

Проверка перед прогоном:

| Что | Как | Ожидание |
|---|---|---|
| Сервис жив | `grpcurl -plaintext localhost:44044 list` | Виден `proto.auth.v1.AuthService` |
| Prometheus видит сервис | `localhost:9090` → Status → Targets | Job `auth-local` в состоянии **UP** |
| Дашборд на месте | `localhost:3000` | «Auth — нагрузка и точки отказа» |

## Запуск

k6 локально ставить не нужно:

```bash
cd shop-auth/load

docker run --rm -i --network host --cpus 4 \
  -v "$PWD:/load" -w /load \
  -e K6_PROMETHEUS_RW_SERVER_URL=http://localhost:9090/api/v1/write \
  -e K6_PROMETHEUS_RW_TREND_STATS='p(99),avg,max' \
  grafana/k6 run -o experimental-prometheus-rw validate.js
```

Переменные:

| Переменная | Значение по умолчанию | Зачем |
|---|---|---|
| `AUTH_ADDR` | `127.0.0.1:44044` | Адрес gRPC |
| `APP_ID` | `1` | Приложение из сидов миграции |
| `USERS` | `50` | Размер пула пользователей для `login.js` и `mixed.js` |
| `CALIBRATE` | — | `-e CALIBRATE=1` заменяет ступени на 1 rps в течение минуты |
| `LOGIN_RATE` / `VALIDATE_RATE` | `100` / `50` | Нагрузка в `mixed.js` |

**Калибровка обязательна перед первым прогоном:**

```bash
docker run --rm -i --network host -v "$PWD:/load" -w /load \
  grafana/k6 run -e CALIBRATE=1 validate.js
```

Должно быть 100% `checks` и стабильная задержка. Ошибки на 1 rps означают дефект сценария, а не предел сервиса.

## Порядок прогонов

| # | Команда | Что ищем |
|---|---|---|
| 1 | Калибровка всех четырёх сценариев | Корректность сценариев |
| 2 | `validate.js`, `login.js`, `refresh.js`, `register.js` по очереди | Колено каждого метода |
| 3 | `mixed.js` с `LOGIN_RATE` ≈ 80% от колена login | Топит ли дорогой метод дешёвые |
| 4 | `validate.js` при `max_open_conns: 5` в `local.yaml` | Как выглядит исчерпание пула |
| 5 | `login.js` при `GOMAXPROCS=1` | Логинов в секунду на одно ядро |
| 6 | `mixed.js` с `LOGIN_RATE=250` (выше колена) | Держит ли семафор на bcrypt: быстрые отказы вместо зависаний, validate не страдает |
| 7 | То же при `password_hasher.max_concurrent: 8` | Сколько login получает от последних двух ядер и чем за это платит validate |

Между прогонами чистить тестовые данные, иначе таблицы растут и цифры поплывут:

```sql
DELETE FROM users WHERE username LIKE 'k6-%';   -- сессии уйдут каскадом
```

## Результаты

Все прогоны: `GOMAXPROCS=8`, TLS выключен, локальный Postgres, k6 в контейнере с `--cpus 4`.

### Методы по отдельности (до семафора на bcrypt)

| Метод | rps на колене | p99 на колене | rps при первых ошибках | Что упёрлось |
|---|---|---|---|---|
| ValidateToken | > 4000, колено не найдено | < 1 мс | ошибок не было | ничего: 0.6 из 8 ядер, одно соединение пула |
| Login | 210 | 466 мс | ошибок не было: выше колена задержка росла до секунд без единого кода ошибки | CPU: bcrypt — около 36 мс процессора на логин, 27 логинов/с на ядро |
| Refresh | > 400, колено не найдено | 2.5 мс | ошибок не было | ничего: 0.43 мс CPU на запрос |
| Register | не прогонялся | — | — | тот же bcrypt, что у Login: хеш p99 50 мс |

Колено — первая ступень, где **одновременно**: p99 вырос непропорционально, фактический rps отстал от заданного, и в ряду «Ресурсы» дашборда что-то встало в потолок. Последняя колонка заполняется по третьему признаку: `go_sql_wait_count_total` — пул, CPU близко к `GOMAXPROCS` — bcrypt.

### Login выше колена вместе с validate

`mixed.js` с `LOGIN_RATE=250 VALIDATE_RATE=50`, 3 минуты — то есть login на 20% выше своего колена.

| | Без семафора | Семафор, 6 слотов (по умолчанию) | Семафор, 8 слотов |
|---|---|---|---|
| Успешные логины | ~216 rps, задержка до 9.84 с | 165 rps, p99 189 мс | 218 rps, p99 236 мс |
| Отказы `ResourceExhausted` | нет: лишние висели до дедлайна | 34%, p99 152 мс | 13%, p99 184 мс |
| Validate: p99 / медиана | 3.4 с / — | **0.40 мс** / 0.23 мс | 34 мс / 12.5 мс |
| Неожиданные ошибки | 1 `Internal` на 48 тыс. | 0 | 0 |
| Пул соединений | 25 из 25, 126 тыс. ожиданий | нет данных | 5 занято, ожиданий 0 |
| Горутины | 2259 | нет данных | ~530 |
| CPU процесса | 8 ядер | нет данных | 7.9 из 8 |

Как это читать:

* **Без семафора — обрыв.** Тысячи bcrypt делят 8 ядер поровну, каждый считается секундами, validate стоит за ними в очереди планировщика, а ждущие горутины держат соединения пула.
* **6 слотов: потолок login = слоты / время bcrypt.** 6 / 0.036 с ≈ 166 rps, замерено 165. Два ядра bcrypt не достаются никогда, и validate отвечает даже быстрее, чем в спокойном режиме (0.5 мс).
* **8 слотов: +32% логинов ценой validate.** 8 / 0.036 с ≈ 222 rps, замерено 218. Но все 8 ядер заняты bcrypt, и validate ждёт ядро: планировщик Go вытесняет горутину примерно раз в 10 мс, отсюда медиана 12.5 мс. По той же причине отказы приходят позже `max_wait` (184 мс против 150): горутине после таймаута тоже нужно дождаться ядра.
* **Поэтому по умолчанию 3/4 от `GOMAXPROCS`.** Validate стоит на пути каждого авторизованного запроса gateway: прибавить 12 мс к каждому вызову API ради 53 логинов в секунду — плохой обмен.
* **Главный эффект — ограничение параллельности, а не резерв ядер.** Даже при 8 слотах система не обрушивается: validate 34 мс против 3.4 с без семафора, пул свободен.

При `GOMAXPROCS=16` (12 слотов) те же 250 rps проходят без отказов за 39 мс: ёмкость login растёт линейно со слотами, то есть с ядрами и инстансами.

## Особенности, на которых легко обжечься

* **Поля ответа приходят в camelCase.** В запросе пишем `email_or_name`, как в proto, а читаем `res.message.accessToken`. Если видишь `undefined` — причина здесь.
* **`connect` нельзя вызывать на init-стадии**, только в `setup` или в VU-коде. И повторный `connect` в том же VU — ошибка, отсюда флаг `connected`.
* **Каждый VU держит своё соединение.** В проде gateway держит одно на всё, поэтому `MaxConcurrentStreams` этими прогонами не проверяется — он про потолок на одно соединение.
* **`refresh.js` ведёт цепочку токенов на каждый VU.** Refresh ротирует токен, старый сразу умирает. Один общий токен дал бы поток `Unauthenticated` со второго запроса — и замер скорости отказов вместо замера ротации.
* **Первая ступень `refresh.js` — разогрев.** На первой итерации каждый VU делает свои Register и Login, то есть платит за bcrypt. Цифры читать со второй ступени.
* **Серверные гистограммы считают от 100 мкс.** Это важно именно для `validate`: со стандартной сеткой Prometheus (от 5 мс) он целиком попадал в первый бакет, и p99 был бесполезен.
* **`GOMAXPROCS` задаёт и размер семафора.** При `max_concurrent: 0` слотов 3/4 от `GOMAXPROCS`. Запуск без `GOMAXPROCS=8` на 16 ядрах даёт 12 слотов и потолок около 300 rps — `mixed.js` на 250 rps тогда проходит без единого отказа и семафор не проверяет. Проверить: `curl -s localhost:8082/metrics | grep auth_password_hash_slots`.

## Чего здесь нет

`Logout` и `IsAdmin` сценариями не покрыты: в проде их доля на порядки меньше, а узкие места у них те же, что у `Refresh` и `ValidateToken`. Смешанный профиль, похожий на реальный трафик, тоже отложен — сначала нужны пределы по отдельным методам, иначе непонятно, что показывает смесь.

## Известные проблемы

* **Стоячая очередь у семафора bcrypt.** Семафор из `x/sync` обслуживает ожидающих по порядку прихода. При устойчивой перегрузке очередь всё время полная, и слот достаётся тому, кто уже прождал почти весь `max_wait`: успешный логин при 6 слотах — медиана 185 мс против 39 мс чистого bcrypt. Пропускную способность это не снижает, только добавляет задержку успешным. Варианты: уменьшить `max_wait` (при 50 мс успешный логин около 90 мс, но очередь поглощает всплеск примерно в 8 запросов сверх слотов вместо 23) или LIFO/CoDel под перегрузкой. Пока оставлено: 185 мс на логин человек не замечает.
* **Пороги на пустых метриках проходят вхолостую.** Если отказов не было (нагрузка ниже потолка), `login_rejected_duration p(99)<250` зелёный при p99 = 0. Это не доказательство, что отказы быстрые, — смотреть на `login_rejected` в сводке.
* **У прогона с 6 слотами нет серверных метрик в отчёте.** Сохранилась только сводка k6, поэтому пул, горутины и CPU в таблице пустые. При следующем прогоне снять их с дашборда или `curl localhost:8082/metrics` в середине нагрузки.


Хороший заход — auth действительно правильное место начинать: он на критическом пути каждого запроса, и если ляжет он, ляжет всё.

Сразу оговорю допущение: план рассчитан на порядок 1–5k rps публичного API и десятки-сотни тысяч активных пользователей. Если цель — 50k+ rps, часть решений меняется (там понадобится шардирование сессий и отдельный edge-слой), скажи, и я перестрою. Ниже отмечаю места, где порог имеет значение.

Сначала диагноз: где именно ляжет
Прежде чем план — три конкретных места. Всё остальное вторично.

1. ValidateToken — главная проблема
Сейчас каждый защищённый запрос к API идёт так:


клиент → gateway → gRPC → auth → ParseToken (~10 мкс) + UserByUUID (SELECT в Postgres)
Разбор JWT стоит микросекунды, а поход в базу — миллисекунды. То есть 99% времени ValidateToken — это запрос к Postgres, и он делается на каждый вызов /products, /cart, любой protected route.

Следствия:

1000 rps публичного API = 1000 SELECT/сек по users только на проверку токенов;
доступность всего API привязана к доступности базы auth;
auth — синхронная зависимость в hot path, её latency складывается с latency каждого запроса.
Это архитектурная проблема, а не проблема оптимизации. Её нельзя решить индексом.

2. bcrypt — CPU-бомба на логине
bcrypt.DefaultCost (10) — это примерно 50–80 мс CPU на одну проверку пароля. Значит одно ядро даёт ~12–20 логинов в секунду, и это 100% его загрузки.

Практический эффект: всплеск логинов (маркетинговая рассылка, редеплой, инвалидация сессий) или credential stuffing забивает все ядра, и ValidateToken с Refresh — дешёвые операции — встают в очередь за дорогими. Сервис «лежит», хотя нагрузка была только на один метод.

Это классический отказ auth-сервиса, и он не лечится масштабированием реплик — атакующий просто нагрузит больше.

3. Пул соединений к Postgres не настроен
В internal/app/app.go после sql.Open не вызваны ни SetMaxOpenConns, ни SetMaxIdleConns, ни SetConnMaxLifetime. Дефолты database/sql: idle = 2, open = без ограничений.

Под нагрузкой это даёт worst case из обоих миров: соединения не переиспользуются (их всего 2 в пуле), а новые открываются без предела, пока Postgres не ответит too many connections (дефолт max_connections = 100, а каждое соединение — отдельный процесс и ~10 МБ на сервере).

Плюс отдельно: без ConnMaxLifetime соединения переживают failover Patroni и продолжают указывать на бывший primary — это я уже отмечал в README, но под нагрузкой оно становится инцидентом, а не неудобством.

Целевая архитектура

flowchart TB
    C["Клиент"]
    subgraph edge["gateway"]
        MW["JWT middleware<br/>локальная проверка подписи<br/>+ deny-list в памяти"]
        RL["rate limit"]
    end
    subgraph auth["auth — только write-path"]
        LG["Login / Register<br/>изолированный пул bcrypt"]
        RF["Refresh"]

        REV["публикация отзыва"]
    end
    RD[("Redis<br/>deny-list по sid")]
    PG[("PostgreSQL<br/>primary + replica")]

    C --> RL --> MW
    MW -. "подпись проверяется<br/>публичным ключом,<br/>без сетевого вызова" .-> JWKS
    MW --> RD
    MW ==>|"protected routes"| API["catalog / cart"]
    C -->|"login / refresh"| LG & RF
    LG & RF --> PG
    REV --> RD
Суть изменения: auth уходит с hot path. Он обслуживает только вход, обновление и регистрацию — операции, которых на порядки меньше, чем обычных запросов к API. Проверка токена становится локальной операцией в gateway.

Ключевое, что делает это возможным без потери мгновенного logout: deny-list нужно держать только на срок жизни access-токена. Отозвали сессию — записали sid в Redis с TTL = TTL токена. Через 15 минут токен истечёт сам, и запись больше не нужна. Размер списка = число отзывов за 15 минут, то есть он крошечный и целиком влезает в память gateway.

Этап 0. Сначала измерить (1–2 дня)
Без этого всё остальное — гадание. Оптимизировать то, что не измерено, — верный способ потратить неделю не на то.

Шаг	Что делаем

Этап 1. Фундамент и блокеры (3–5 дней)
Дешёвые правки, без которых остальное бессмысленно измерять.

1.1 Пул соединений


db.SetMaxOpenConns(25)                   // на инстанс; 4 инстанса × 25 = 100 ≈ max_connections
db.SetMaxIdleConns(25)                   // == MaxOpen: не даём пулу «сдуваться» между всплесками
db.SetConnMaxLifetime(5 * time.Minute)   // обязательно из-за HAProxy + Patroni failover
db.SetConnMaxIdleTime(1 * time.Minute)
MaxIdleConns == MaxOpenConns — важная деталь: при меньшем idle пул постоянно закрывает и открывает соединения, а установка соединения к Postgres стоит дороже самого запроса.

Число 25 — стартовая точка, финальное значение из этапа 0. Правило: MaxOpenConns × число_инстансов < max_connections − запас_на_миграции_и_админа.

Если инстансов будет больше 4–5, нужен PgBouncer в transaction pooling — иначе арифметика не сойдётся. Тогда же стоит рассмотреть переход с database/sql на pgxpool (заметно дешевле по аллокациям, но теряется database/sql-совместимость).

1.2 Исправить определение уникальности

internal/storage/postgres/storage.go импортирует github.com/jackc/pgconn (v1), а драйвер — pgx/v5, который возвращает *pgconn.PgError из github.com/jackc/pgx/v5/pgconn. Разные типы → errors.As не срабатывает никогда, и определение дубликата держится на strings.Contains(err.Error(), "SQLSTATE 23505"). Меняем импорт, убираем fallback.

1.3 Таймауты и лимиты на gRPC-сервере

Сейчас в internal/app/grpc/app.go нет ни одного ограничения:


grpc.MaxConcurrentStreams(1000),
grpc.KeepaliveParams(keepalive.ServerParameters{
    MaxConnectionIdle: 5 * time.Minute,
    Time:              30 * time.Second,
    Timeout:           10 * time.Second,
}),
grpc.KeepaliveEnforcementPolicy(keepalive.EnforcementPolicy{
    MinTime:             10 * time.Second,
    PermitWithoutStream: false,
}),
Плюс unary-интерцептор, который навешивает дедлайн, если клиент его не передал. Сейчас запрос без дедлайна может висеть неограниченно, удерживая соединение из пула.

1.4 Чистка мёртвого кода

Удалить internal/clients/client/ (ломает go build ./...), internal/storage/sqlite/ (364 строки, не подключено), cmd/gateway/ (второй HTTP-гейтвей с CORS, ходит по insecure gRPC). Это не косметика: мёртвый код в auth-сервисе — это поверхность атаки, которую никто не ревьюит.

1.5 Консистентность: is_active

Login и Refresh не проверяют user.IsActive, а ValidateToken проверяет. Деактивированный пользователь получает рабочую пару токенов, которая тут же не работает. Добавить условие прямо в SQL (AND is_active), а не в Go — так проверку нельзя забыть в новом методе.

Этап 2. Убрать auth с hot path (1.5–2 недели)
Самый крупный и самый важный этап. Он же закрывает проблему logout, описанную в README gateway.

2.1 Перейти на асимметричную подпись

Сейчас HS256 с секретом из apps.secret. Симметричный ключ означает, что проверяющий может и выпускать — поэтому локальная валидация в gateway невозможна без передачи ему права подписи.

Переход на ES256 (или RS256, но ES256 даёт подписи вчетверо короче и быстрее проверяется):

Что	Где
Приватный ключ	только в auth, из Vault
Публичный ключ	раздаётся всем через GET /.well-known/jwks.json
kid в заголовке токена	чтобы поддерживать несколько ключей одновременно — это то, что делает ротацию возможной без разрыва
Ротация ключей становится штатной операцией: публикуем новый ключ в JWKS, ждём, пока все потребители его увидят, начинаем подписывать новым, старый держим в JWKS до истечения последнего выданного им токена.

2.2 Новый набор claims


{
  "iss": "shop-auth",
  "sub": "<user uuid>",
  "aud": ["shop-api"],
  "sid": "<session uuid>",
  "jti": "<token uuid>",
  "app_id": 1,
  "roles": ["user"],
  "iat": 1700000000,
  "exp": 1700000900
}
Что добавилось и зачем:

sid — идентификатор сессии. Основа отзыва: отзываем сессию, а не отдельный токен, поэтому refresh не сможет выпустить новый access, и уже выданный тоже перестанет приниматься.
roles — избавляет от вызова IsAdmin на каждую проверку прав. Роль меняется редко, а токен живёт 15 минут — задержка приемлема и контролируема.
iss / aud — без них токен, выпущенный для одного получателя, принимается другим.
jti — для точечного отзыва и аудита.
2.3 Deny-list с ограниченным сроком


sequenceDiagram
    participant U as Клиент
    participant A as auth
    participant R as Redis
    participant G as gateway

    U->>A: Logout(refresh_token)
    A->>A: revoked_at на refresh-сессии
    A->>R: SADD revoked:sid <sid>, TTL = access_ttl
    Note over R: запись живёт 15 минут —<br/>ровно столько, сколько мог бы<br/>прожить выданный access-токен
    G->>R: периодический SCAN / pub-sub
    G->>G: обновление in-memory deny-list
    U->>G: запрос с отозванным токеном
    G->>G: подпись валидна, но sid в deny-list
    G-->>U: 401
Ключевая мысль, которая делает схему дешёвой: запись в deny-list нужна только на TTL access-токена. Дальше токен истекает сам. Значит размер списка = число отзывов за 15 минут — это единицы или десятки записей, они целиком живут в памяти gateway, и проверка стоит наносекунды без всякой сети.

Redis тут — канал распространения между репликами gateway, а не хранилище на горячем пути.

2.4 Валидация в gateway вместо gRPC-вызова

Middleware в shop-gateway-service/internal/transport/http/v1/middleware/auth.go вместо authService.ValidateToken(...) делает:

разобрать токен, проверить подпись публичным ключом из кэша JWKS;
проверить exp, iss, aud;
проверить, что sid не в deny-list;
положить sub, app_id, roles в контекст.
Ни одного сетевого вызова. Порядок величины — десятки микросекунд на запрос вместо миллисекунд.

ValidateToken в gRPC-контракте остаётся — он нужен для сервисов, которым проще спросить, чем валидировать самим, и как отладочный инструмент. Но с hot path он уходит.

2.5 Компромисс, который надо принять осознанно

Мгновенность отзыва теперь ограничена не проверкой в базе, а скоростью распространения deny-list между репликами gateway (pub/sub — сотни миллисекунд, периодический опрос — до интервала опроса). Для деактивации пользователя админом это нормально. Если нужна строгая мгновенность для отдельных операций (смена пароля, удаление аккаунта), для них можно оставить синхронный вызов в auth — таких запросов единицы.

Ожидаемый эффект этапа: нагрузка на auth падает с «каждый запрос API» до «вход + обновление раз в 15 минут на пользователя». Это снижение на 1–2 порядка.

Этап 3. Защита от перегрузки (1 неделя)
Теперь, когда auth обслуживает только write-path, надо сделать так, чтобы дорогие операции не топили дешёвые.

3.1 Bulkhead для bcrypt


type PasswordHasher struct {
    sem chan struct{}   // размер = GOMAXPROCS, максимум GOMAXPROCS+1
}

func (h *PasswordHasher) Compare(ctx context.Context, hash, password []byte) error {
    select {
    case h.sem <- struct{}{}:
        defer func() { <-h.sem }()
    case <-ctx.Done():
        return ErrOverloaded      // отдаём 503, а не встаём в очередь
    }
    return bcrypt.CompareHashAndPassword(hash, password)
}
Смысл: bcrypt намеренно CPU-bound, и запускать его в неограниченном числе горутин бессмысленно — они всё равно конкурируют за те же ядра, но при этом раздувают память и latency. Семафор размером в число ядер даёт максимальную пропускную способность и оставляет процессору возможность обслуживать Refresh.

Отказ по переполнению (503 + Retry-After) — это то, что отличает деградацию от падения: часть клиентов получает честный отказ, остальные работают.

3.2 Rate limiting на уровне auth

Лимитер gateway работает по IP и не спасает от подбора пароля с распределённых адресов. Нужны отдельные лимиты:

Лимит	Ключ	Порядок значения
Попытки логина на аккаунт	login:user:<email>	5–10 в 15 минут
Попытки логина с IP	login:ip:<ip>	20–50 в минуту
Регистрации с IP	register:ip:<ip>	3–5 в час
Refresh на сессию	refresh:sid:<sid>	10 в минуту
Лимит на аккаунт с экспоненциальной задержкой — основная защита от credential stuffing. Он же защищает CPU: атака гасится до того, как дойдёт до bcrypt.

3.3 Admission control и circuit breaker

Общий лимит одновременных запросов на инстанс → при превышении ResourceExhausted, а не бесконечная очередь.
Circuit breaker на Postgres: если база не отвечает, размыкаем и отдаём Unavailable быстро, вместо того чтобы держать соединения и копить таймауты. Дешевле для базы — она успевает восстановиться.
Приоритизация: Refresh и ValidateToken важнее Register. При перегрузке регистрации отбрасываются первыми.
3.4 Джиттер в TTL токенов

Неочевидное, но важное: если access-токены выдаются с одинаковым TTL, то после массового события (редеплой, инвалидация, утренний пик входов) все они истекают почти одновременно → синхронный шторм refresh-запросов, который придёт ровно в тот момент, когда сервис только поднялся.

Решение — случайный разброс ±10% к token_ttl при выпуске. Одна строка, снимает целый класс инцидентов.

Этап 4. Данные под нагрузкой (1–1.5 недели)
4.1 Рост user_sessions

Считаем: 100k активных пользователей, access TTL 15 минут → каждый обновляется 4 раза в час. Каждый refresh = транзакция с INSERT + UPDATE. Это ~110 записей/сек и ~9.5 млн строк в сутки, которые сейчас не удаляются никогда.

Нужно:

джоба очистки: DELETE WHERE expires_at < now() - interval '7 days' порциями по 10k (не одним запросом — он возьмёт долгую блокировку и раздует WAL);
либо партиционирование по expires_at с DROP PARTITION — на таких объёмах это единственный масштабируемый вариант, удаление партиции мгновенно и не создаёт bloat;
autovacuum настроить агрессивнее именно на эту таблицу (autovacuum_vacuum_scale_factor = 0.02) — при таком потоке UPDATE дефолтные настройки не успевают, и таблица распухнет.
4.2 Индексы под фактические запросы

RefreshSessionByHash ищет по (refresh_token_hash, device_id, app_id), а индекс есть только на refresh_token_hash (через UNIQUE). Составной индекс под фактический предикат + INCLUDE (user_uuid, expires_at, revoked_at) даст index-only scan, то есть чтение без обращения к heap.

Проверить EXPLAIN (ANALYZE, BUFFERS) на User() — он ищет WHERE email = $1 OR username = $1, и на OR планировщик может выбрать неоптимальный план. Возможно, стоит разделить на два запроса или сделать выражательный индекс.

4.3 Обнаружение переиспользования refresh-токена

Схема уже хранит replaced_by_hash, но код на него не реагирует. Между тем повторное предъявление уже заротированного токена — главный признак кражи: либо токен украли и им воспользовались, либо им воспользовались после того, как украли легитимный.

Штатная реакция: отозвать всю цепочку сессий пользователя и потребовать повторный вход. Это и consistency, и безопасность одновременно.

Заодно добавить FOR UPDATE в SELECT внутри транзакции ротации — сейчас корректность спасает проверка RowsAffected, что работает, но выражает намерение неявно.

4.4 Read replica для чтений (если останутся)

После этапа 2 чтений в auth почти не остаётся, поэтому это опционально. Если понадобится — HAProxy сейчас отдаёт только primary (один frontend на /primary), нужен второй frontend на /replica. И осознать компромисс: только что деактивированный пользователь может успешно провалидироваться через реплику в пределах лага репликации.

4.5 Кэш секретов/ключей с TTL и singleflight

JWTAdapter.appCache сейчас кэширует навсегда — ротация ключа не подхватится до рестарта. Добавить TTL, а вместе с ним обязательно golang.org/x/sync/singleflight: иначе при истечении TTL под нагрузкой все горутины разом пойдут в базу за одним и тем же ключом (cache stampede).

Сейчас 3 тестовых файла, и интеграционные требуют руками поднятого окружения на порту 5454. Для сервиса, который держит нагрузку, этого недостаточно.

Отдельно — тест на потерю транзакций при failover. Репликация асинхронная (в patroni-конфигах нет synchronous_mode, а maximum_lag_on_failover: 1048576), то есть failover может потерять подтверждённые регистрации. Это нужно либо принять осознанно и задокументировать, либо включить synchronous_mode: true и заплатить latency записи. Для auth я бы включил: терять созданных пользователей хуже, чем отвечать на 5 мс медленнее.

Этап 6. Эксплуатация (1 неделя)
6.1 Секреты в Vault — это ваша заявленная следующая фаза, и здесь она сходится с этапом 2: приватный ключ подписи вообще не должен лежать на диске. Убрать сидирование секретов из миграции 000001 (web-secret, mobile-secret — это ключи HS256 открытым текстом).

6.2 Нулевой downtime при деплое

Миграции по схеме expand/contract: сначала совместимое расширение схемы, деплой кода, потом удаление старого. Иначе любой деплой = окно недоступности.
Graceful shutdown уже есть, но нужен drain period: health → NOT_SERVING, подождать 2–3 интервала проверки балансировщика, потом останавливать приём. Сейчас переключение статуса и остановка происходят слитно, и часть запросов получит отказ.
6.3 Аудит

Таблицы audit_logs и модель AuditLog созданы, но не пишутся. Для auth-сервиса в проде это обязательное, а не опциональное: LOGIN_OK, LOGIN_FAIL, REFRESH_OK, REFRESH_REUSE_DETECTED, LOGOUT, PASSWORD_CHANGED. Комментарий в схеме уже перечисляет ожидаемые значения.

Писать не в синхронном пути — через тот же транзакционный outbox, что в каталоге, иначе аудит станет ещё одной записью в базу на каждый логин.

6.4 Публикация событий

Заодно закрывается разрыв с notification: auth.user.registered через outbox → RabbitMQ. Сервис уведомлений полностью готов их принимать, publisher'а нет.

Чего я бы не делал
Чтобы не потратить время не туда:

Не переписывать на другой фреймворк. Текущая слоистая структура (transport → service → storage через узкие интерфейсы) нормальная, её не надо ломать. Проблемы архитектурные (auth на hot path), а не структурные.
Не выносить сессии в отдельный сервис. На заявленном порядке нагрузки это лишняя сетевая граница.
Не кэшировать результат ValidateToken в Redis как быстрое решение. Это выглядит соблазнительно (одна правка вместо этапа 2), но оставляет auth в hot path, добавляет проблему инвалидации и даёт выигрыш только в latency, не в связанности. Локальная валидация лучше по всем параметрам.
Не переходить на argon2id просто потому, что он современнее. bcrypt cost 10 — адекватная защита. Проблема не в алгоритме, а в отсутствии bulkhead и rate limiting. Если менять — то после измерений и с явным подбором параметров под ваш CPU-бюджет.
Не шардировать базу. До сотен тысяч rps не понадобится; сначала read replica и PgBouncer.
