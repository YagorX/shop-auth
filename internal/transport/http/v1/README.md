# internal/transport/http/v1

HTTP-слой сервиса. Здесь **нет бизнес-API** — весь auth-flow идёт по gRPC. Порт `:8082` существует для эксплуатации: проверок живости, метрик и управления логированием на работающем процессе.

## Маршруты

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/health` | `200` всегда, пока процесс отвечает |
| `GET` | `/ready` | `200` если `db.PingContext` успешен, иначе `503` |
| `GET` | `/metrics` | Prometheus-формат |
| `GET` | `/admin/log-level` | Текущий уровень |
| `POST` | `/admin/log-level` | Сменить уровень: `debug`, `info`, `warn`, `error` |

## Разделение health и ready

Это не дублирование, а два разных вопроса:

* `/health` — «процесс не завис, перезапускать не нужно». Не зависит ни от чего внешнего.
* `/ready` — «можно направлять трафик». Зависит от PostgreSQL.

Если смешать их в одну проверку, кратковременная недоступность базы приведёт к перезапуску контейнера, который ничем не поможет — база всё равно недоступна. Разделение позволяет вывести инстанс из балансировки, не убивая его.

## Структура

```text
http/v1/
├── router.go         # сборка mux, обёртка метрик, Recovery
├── contracts/        # интерфейсы: LogLevelController, ReadinessChecker
├── handlers/         # health, admin
└── middleware/
    ├── chain.go      # композиция
    └── recovery.go   # перехват паник
```

`contracts/ports.go` объявляет то, что роутеру нужно от внешнего мира. `ReadinessChecker` реализован в `internal/app`, `LogLevelController` — в `internal/observability`. Роутер не знает ни про `*sql.DB`, ни про `slog.LevelVar`.

## Цепочка middleware

```mermaid
flowchart LR
    R["Запрос"] --> REC["Recovery"]
    REC --> M["обёртка метрик<br/>statusRecorder"]
    M --> MUX["ServeMux"]
    MUX --> H["handler"]
```

`Chain` применяет middleware в обратном порядке, так что первым в цепочке оказывается `Recovery` — паника в любом хендлере будет перехвачена и превращена в `500` с JSON-телом вместо разрыва соединения.

`statusRecorder` — минимальная обёртка над `http.ResponseWriter`, перехватывающая `WriteHeader`, чтобы узнать итоговый статус для метрики. По умолчанию `200`: если хендлер ничего не писал явно, Go отдаст именно его.

## Управление уровнем логов

`/admin/log-level` работает через `slog.LevelVar` — атомарную переменную, которую держит `RuntimeLogger`. Смена уровня видна немедленно во всех горутинах, перезапуск не нужен.

```bash
curl http://localhost:8082/admin/log-level
curl -X POST "http://localhost:8082/admin/log-level?level=debug"
```

Практический смысл: включить `debug` на время разбора инцидента и выключить, не теряя процесс и его состояние.

## Известные проблемы

* **Неограниченная кардинальность метрик.** [`router.go`](router.go) передаёт `r.URL.Path` в метку `path` без нормализации. Запрос на `/whatever-123` создаёт новый time series в Prometheus. Так как эндпоинтов всего четыре, достаточно маппить неизвестные пути в `"other"` или брать шаблон маршрута вместо фактического пути.
* **`/admin/log-level` без аутентификации.** Порт 8082 публикуется на хост в compose. Смена уровня на `debug` в проде — это и рост объёма логов, и потенциальная утечка деталей в них. Сравни с `shop-proxy`, где `/admin/*` закрыт middleware через `ValidateToken` + `IsAdmin`.
* **`deps.LogLevelController.GetSlog()` вызывается без проверки на nil** — если зависимость не передали, роутер упадёт на этапе сборки, а не вернёт ошибку.
